## 4. 정성적 품질 차이 (CoT의 실질적 가치)

F1-Score는 동일하지만, **리포트의 품질**에서 유의미한 차이가 존재합니다.

### 4.1 설명 깊이 비교

**방식 A (No-CoT) - VULN-002 eval 취약점:**
> "mathFormula 값을 검증 없이 eval()에 전달하여 임의의 코드 실행이 가능합니다."

**방식 B (CoT) - 동일 취약점:**
> "mathFormula 값을 검증 없이 eval()에 그대로 전달하고 있습니다. eval()은 입력 문자열을 JavaScript 코드로 해석하므로, 단순 수식뿐 아니라 시스템 명령 실행, 프로세스 접근, 민감정보 노출 등 임의 코드 실행으로 이어질 수 있습니다."
>
> **exploit_scenario**: "공격자가 mathFormula에 `process.mainModule.require("child_process").execSync("id")` 같은 페이로드를 전송하면..."
>
> **decision_tree**: ["클라이언트가 mathFormula를 POST 본문으로 보낸다" → "서버는 해당 값을 아무 검증 없이 eval()에 전달한다" → "eval()은 문자열을 코드로 실행한다" → "공격자는 수식 대신 임의 JavaScript 코드를 주입할 수 있다" → "결과적으로 원격 코드 실행 및 서버 장악이 가능하다"]

## 5. 종합 결론

### 토큰 효율성 (멀티 에이전트)
- **단일 파일 스캔**: 멀티 에이전트가 **2.5배 더 많은 토큰** 사용 (코드 2번 읽기 오버헤드)
- **대규모 프로젝트 (예상)**: Nano 필터링률이 60~80%라면, Mini 모델 호출 횟수가 그만큼 감소하여 **총 토큰 40~60% 절감 예상**
- **결론**: 멀티 에이전트 구조는 **파일 수가 많을수록 효과적**. 단일 파일에서는 오히려 비효율적.

### 탐지 품질 (CoT)
- **정량적 F1-Score**: 동일 (0.5714). 이번 테스트에서 CoT가 추가 취약점을 발견하지는 못함.
- **정성적 리포트 품질**: 방식 B가 현저히 우수. 공격 시나리오, 추론 과정, 데이터 흐름 분석이 포함되어 **보안 감사 보고서로서의 완성도가 높음**.
- **결론**: CoT는 **탐지 수(Recall)보다 탐지 설명의 품질과 신뢰성**을 높이는 데 기여.

### 한계 및 향후 개선

1. **테스트 규모 확대 필요**: 단일 파일(83줄) 테스트로는 멀티 에이전트의 토큰 절감 효과를 증명하기 어려움. 수십 개 파일로 구성된 프로젝트 단위 테스트가 필요.
2. **정답지 난이도 조정**: VULN-008(타이밍 공격), VULN-009(경쟁 조건)는 정적 분석의 본질적 한계에 해당하여 정답지에서 제외하거나 별도 카테고리로 분류하는 것이 공정.
3. **반복 실행 필요**: LLM의 확률적 특성상 1회 실행 결과만으로 결론을 내리기 어려움. 동일 조건에서 5~10회 반복 실행 후 평균값을 사용하는 것이 통계적으로 타당.
