## Problem Statement

현재 실행 경로가 `run_ui.bat`, `scan_project.bat`, CLI 전용 `main.py`, `ui/app.py`로 나뉘어 진입점이 불명확하다. UI는 로컬 폴더만 받고 단일 진행 문구와 최종 결과만 표시한다. 에이전트 분석은 컨텍스트마다 NVIDIA 호환 API를 호출하므로 무료 키의 호출 제한에 불리하다.

목표는 `python main.py` 하나로 로컬 Streamlit UI를 열고, 경로 또는 업로드 파일을 안전하게 분석하며, Semgrep부터 최종 보고서까지 실제 처리 순서와 중간 결과를 표시하는 것이다. 분석 입력은 크기 제한이 있는 묶음 단위로 호출해 API 호출 수를 줄인다.

## What Makes This Cool

- 정적 분석 결과가 정탐·미탐 판단과 개선안으로 변하는 과정을 한 화면에서 추적한다.
- 무료 NVIDIA 키에서도 입력별 호출 대신 크기 기반 배치를 사용한다.
- 설치 후 기억할 실행 명령은 `python main.py` 하나다.

## Constraints

- 로컬 단일 사용자, 한 번에 한 스캔을 기준으로 한다.
- NVIDIA의 별도 Batch API가 아닌 애플리케이션 수준 묶음 요청을 사용한다.
- 기존 LangGraph 분석·도구 호출과 JSON/Markdown/SARIF 보고서를 최대한 재사용한다.
- API 키와 전체 소스는 이벤트·로그·보고서에 노출하지 않는다.
- 별도 작업 서버, DB, 인증, 원격 배포는 제외한다.

## Premises

1. `main.py`는 명시적인 자식 환경 플래그로 Streamlit을 한 번만 시작한다.
2. UI는 동기 파이프라인의 구조화 이벤트로 갱신하며 작업 큐를 추가하지 않는다.
3. 배치는 항목 수, canonical JSON 문자 수, 보수적 토큰 추정치를 모두 제한한다.
4. 입력은 로컬 디렉터리, ZIP 프로젝트 1개, 복수 소스 파일 중 하나다.
5. Semgrep, 에이전트 분석, 검증, 보고서 snapshot을 모두 보존한다.
6. 업로드는 실행별 임시 작업공간에서 검사하고 성공·실패 모두 정리한다.

## Approaches Considered

### Approach A: 최소 래퍼

기존 `ui/app.py`를 유지하고 `main.py`가 이를 실행한다. 고정 개수 배치와 ZIP 업로드만 추가한다. 수정량은 작지만 큰 입력이 한 배치에 몰리고 단계 결과 계약이 UI에 종속된다.

### Approach B: 구조화된 단일 UI와 크기 기반 배치

`main.py`를 유일한 진입점으로 만들고, 타입이 있는 단계 이벤트와 결과 snapshot을 추가한다. 입력을 크기로 묶고 결과를 ID로 복원한다. 업로드 경계는 별도 모듈로 격리한다.

### Approach C: 백그라운드 작업 플랫폼

작업 큐, 실행 이력, 재개, 다중 사용자 상태를 추가한다. 장시간 원격 서비스에는 유용하지만 로컬 포트폴리오 범위를 벗어난다.

## Recommended Approach

Approach B를 선택한다. 호출 수 감소, 단계별 관찰 가능성, 안전한 업로드를 제공하면서 기존 동기 파이프라인을 유지할 수 있다.

### 실행 구조와 호환성

```text
python main.py
  +-- AGENTIC_SAST_STREAMLIT_CHILD 없음
  |    +-- AGENTIC_SAST_STREAMLIT_CHILD=1 python -m streamlit run main.py
  +-- AGENTIC_SAST_STREAMLIT_CHILD=1
       +-- render_app() -> run_pipeline(target, key, on_event)
```

Streamlit 내부 API 감지 대신 부모가 자식에게만 전달하는 플래그로 재귀를 막는다. `sys.executable`과 인자 배열을 사용하고 shell 문자열을 만들지 않는다. 부모는 자식 종료 코드를 반환하고 인터럽트 시 자식 종료를 기다린다. `.streamlit/config.toml`의 localhost, XSRF, CORS 설정을 적용한다.

`main.py`는 자식 프로세스 부트스트랩과 플래그 분기만 담당한다. 자식 분기에서만 부작용 없는 `ui.app.render_app()`을 지연 import한다. `ui/app.py`는 모듈 import 시 Streamlit 위젯을 만들거나 분석을 시작하지 않는다.

사용자가 요청한 breaking change로 `run_ui.bat`, `scan_project.bat`, 기존 `main.py --target` CLI를 제거한다. README는 `python main.py` 단일 UI 명령으로 교체한다. headless CLI는 이번 범위에 없다. 과거 `codex_works` 기록은 수정하지 않는다.

### Streamlit 실행 상태

- `st.session_state`에 `run_id`, `run_status`, 네 단계 snapshot, artifact bytes를 보존한다.
- 분석 중에는 입력과 시작 버튼을 비활성화해 중복 제출과 입력 변경을 막는다.
- 앱은 동기 분석 중 자체 rerun을 일으키지 않는다. 분석이 완료·실패로 반환된 뒤의 rerun만 저장된 snapshot을 다시 그리며 새 분석을 자동 시작하지 않는다.
- 완료·실패 후 재실행하면 새 `run_id`로 이전 화면 상태를 교체한다.
- `core.pipeline`의 기존 `_SCAN_LOCK`을 프로세스 전역 `RunCoordinator`로 승격해 lock, 활성 `run_id`, 시작 시각을 관리한다. UI와 `run_pipeline`이 같은 coordinator를 사용하며 새 세션·탭은 활성 run이 있으면 새 분석을 시작하지 않고 “다른 분석 실행 중”을 표시한다.
- 새로고침·이탈 시 서버 작업의 지속·취소·snapshot 재연결을 보장하지 않는다. 호출이 정상 반환하거나 stack이 중단되면 `finally`에서 lock을 해제하고, 프로세스 종료 시 process lock이 해제된다. 이번 버전에는 취소·재연결 기능이 없다.
- 진행 콜백은 기존 placeholder만 갱신하며 전체 앱 rerun을 호출하지 않는다.
- `.env` 또는 프로세스 환경의 `NVIDIA_API_KEY`는 자동 감지한다. UI 직접 입력은 저장 기능 없는 실행별 override이며 검증 후 지역 변수로만 전달하고 widget/session state 값은 실행 `finally`에서 제거한다. 키는 event, snapshot, artifact, 예외 문자열에 포함하지 않는다.
- session에는 최신 run 하나만 유지한다. 새 run 시작 전에 이전 snapshot과 artifact bytes를 제거하며 source 전문은 저장하지 않는다. snapshot canonical JSON은 20 MiB, 다운로드 artifact 합계는 50 MiB를 넘으면 초과 데이터를 보존하지 않고 명확한 warning을 표시한다.

### 입력과 임시 작업공간

- 라디오로 `로컬 경로`와 `파일 업로드` 중 하나만 활성화한다.
- 업로드는 ZIP 1개 또는 일반 소스 파일 여러 개를 받는다. 혼합 입력은 거부한다.
- OS 임시 디렉터리 아래 실행별 고유 작업공간을 만든다.
- ZIP 엔트리는 정규화 후 작업공간 내부인지 확인한다. 절대·드라이브·`..` 경로, 중첩 ZIP, symlink, junction, 장치, FIFO를 거부한다.
- 모든 엔트리 목적지를 추출 전에 NFC Unicode, Windows case-fold, 후행 점·공백 제거 규칙으로 canonicalize한다. 중복 엔트리, 정규화 후 충돌, Windows 예약명은 전체 ZIP을 거부한다.
- 기본 한도는 업로드 25 MiB, 파일당 2 MiB, 파일 500개, 총 해제 100 MiB, 압축률 100:1이다.
- 해제 도중 한도를 넘으면 실행 전체를 원자적으로 실패시키고 작업공간을 삭제한다.
- 기존 민감 파일·경로 정책을 재사용한다. 로컬 경로는 symlink/junction을 따라가지 않고 최대 10,000개 엔트리까지만 순회한다.
- 읽을 수 없는 로컬 항목은 경고로 남긴다. 분석 가능한 파일이 없으면 입력 실패다.
- 일반 파일 업로드는 basename 기준으로 루트에 둔다. 동일 basename은 거부하며 디렉터리/import 관계 보존이 필요하면 ZIP을 안내한다.
- 업로드 결과 PDF/HTML, XLSX, JSON은 삭제 전 bytes로 보존하고 `finally`에서 작업공간을 정리한다. 로컬 분석은 기존 산출 경로도 유지한다.

### 배치 계약

입력 순서를 유지하는 greedy packing을 사용한다.

- `project_tree` 같은 실행 공통 메타데이터는 batch envelope에 한 번만 직렬화하고 개별 context에서는 제거한다. 공통 envelope 크기도 모든 문자·토큰 예산 계산에 포함한다.

- 기본 최대 8개 항목, canonical JSON 24,000자, 추정 입력 12,000토큰, 출력 예약 4,000토큰이다.
- 기본 토큰 상한은 공통 prompt와 JSON overhead를 포함한 `UTF-8 byte count`로 계산한다. 대상 모델의 tokenizer adapter가 live spike에서 검증된 경우에만 정확 계산으로 교체한다. 문자·토큰 제한을 모두 만족해야 같은 배치에 넣는다.
- 모델이 context-length 오류를 반환하면 배치를 절반으로 나눠 한 번 재시도한다.
- 단일 항목이 넘치면 `truncated=true`로 표시한다. ID, 파일, 시작·끝 라인, rule ID, severity, 취약 코드 주변 최소 20줄을 우선 보존한다.
- 메타데이터와 20줄도 hard limit을 넘으면 줄 수와 UTF-8 byte를 제한까지 줄인다. 필수 메타데이터만으로도 넘으면 해당 항목을 `error/input_too_large`로 종료하고 호출하지 않는다.
- `finding_id`는 `[source_kind, NFC+casefold normalized_path, start_line, end_line, rule_id, ordinal]` canonical JSON의 SHA-256 앞 20자로 만들어 실행 간 안정적으로 유지한다. `context_id`는 `[run_id, finding_id]` canonical JSON hash로 만들고 실행 중 배치 매핑에 사용한다. 둘 다 충돌을 검사하며 재시도·분할에서 유지한다.
- 요청은 JSON 배열을 받고 동일 ID의 JSON 결과 배열을 반환한다. 누락·중복·미등록 ID를 검증한다.
- 유효한 부분 결과는 보존하고 누락 항목만 작은 배치로 한 번 재시도한다.
- HTTP 408/429/500/502/503/504는 최대 2회 재시도한다. 기본 1초, 지수 backoff 최대 15초, jitter 20%이며 `Retry-After`는 최대 30초다.
- JSON parsing/schema 오류는 배치 분할 재시도 1회만 허용한다.
- 동시성은 1로 고정한다.
- `max_llm_requests` 기본값 250을 유지한다. 최초 호출, HTTP 재시도, 분할 재시도, 단건 보강을 모두 1회씩 차감한다.
- 예산 소진 시 남은 항목은 `skipped`로 기록하고 확보한 결과로 부분 보고서를 만든다.

모델 context 한도는 `NVIDIA_CONTEXT_WINDOW_TOKENS`로 명시하며 기본 32,768, 허용 범위 8,192~1,048,576이다. `estimated_input + output_reserve`가 이 값을 넘으면 시작 전에 설정 오류로 중단한다. 단일 항목이 분할·절단 뒤에도 context-length 오류를 내면 `error/model_context_exceeded`로 종료한다.

단건·배치가 공통 `normalize -> verify IDs -> map -> report` 경계를 사용한다. 각 배치는 1차 분석 LLM 1회와 독립 검증 LLM 1회로 처리해 정탐·미탐 역할을 분리한다. 분석 결과가 `needs_tool=true`이고 high/critical이거나 confidence 0.7 미만인 항목만 기존 도구 흐름으로 넘긴 뒤, 해당 항목의 보강 근거를 다음 배치 검증에 포함한다. 보강은 실행당 10개, 항목당 2 tool round로 제한하고 별도 호출로 표시한다.

`core/batch_analysis.py`가 DTO, deterministic packer, canonical ID, 응답 schema 검증, retry/분할, 요청 통계를 소유한다. `core/agent.py`는 LLM 인스턴스와 LangGraph 단건 도구 보강을 제공하고, `core/pipeline.py`는 단계 순서와 snapshot 조립만 담당한다.

각 배치는 `BatchOutcome(status, results, errors, attempts, request_count)`을 반환한다. 예상 가능한 HTTP, context, parsing, schema, budget 오류는 고유 `error_code`로 변환한다. 모듈 경계의 마지막 방어 외에는 광범위한 `except Exception`으로 빈 배열을 반환하지 않으며, 빈 정상 결과와 실패 결과를 구분한다.

Semgrep은 API 키 없이 먼저 실행한다. findings가 0개면 키 검증 없이 빈 보고서를 만들고, 분석 후보가 있을 때만 NVIDIA 키와 모델 설정을 검증한다.

NVIDIA 구조화 출력은 구현 첫 단계에서 실제 키로 두 항목의 ID 왕복 spike를 수행한다. 지원되면 JSON schema 응답을 사용하고, 미지원이면 JSON-only prompt와 로컬 schema 검증을 사용한다. 두 경로는 같은 parser와 ID 검증 테스트를 통과해야 한다.

### 단계 이벤트와 결과 모델

```text
StageEvent
  run_id
  stage: semgrep | agent | verification | report
  status: pending | running | completed | partial | failed | skipped
  current / total
  message / error_code
  payload
```

단계 payload 타입:

- `semgrep`: findings, severity/rule counts
- `agent`: batch_id, item_ids, analyses, request_stats
- `verification`: results, verdict counts
- `report`: artifact metadata, summary

각 결과에 `context_id`, `status`, `message/error_code`가 필수다. Semgrep 이후 결과는 원본 파일·라인을 유지한다. callback payload에는 API 키나 전체 소스 대신 표시용 요약과 ID만 담고 `PipelineResult`가 최종 권위 데이터가 된다.

분석 결과 schema는 다음 필드를 고정한다.

```text
AgentAnalysis
  context_id: non-empty string
  status: ok | error | skipped
  vulnerability_type: string | null
  severity: critical | high | medium | low | info | null
  confidence: float 0.0..1.0 | null
  needs_tool: boolean
  summary: string
  evidence: [{path, start_line>=1, end_line>=start_line}]
  improvement: string
  error_code: string | null

VerificationResult
  context_id: non-empty string
  verdict: tp | fp | unknown | error | skipped
  confidence: float 0.0..1.0 | null
  rationale: string
  improvement: string
  source: {path, start_line, end_line}
  error_code: string | null
```

`ok` 결과는 summary와 evidence가 필수다. `tp|fp|unknown`은 rationale이 필수다. `tp`에는 remediation 의미의 improvement, `fp`에는 Semgrep rule/context 개선안, `unknown`에는 추가 확인 방법을 기록한다. `error|skipped`는 error_code가 필수다.

`PipelineResult`는 `semgrep_findings`, `agent_analyses`, `verification_results`, `approved_findings`, `artifacts`, `warnings`, `request_stats`를 가진다. 검증 verdict는 `tp | fp | unknown | error | skipped`다. `tp`만 최종 승인하고 나머지도 근거·개선안·상태와 함께 UI/부분 보고서에 남긴다.

상태는 `pending -> running -> completed|partial|failed`, 선행 실패로 미실행이면 `pending -> skipped`다. skipped 단계는 시작 이벤트 없이 terminal 이벤트 한 번만 낸다. 이벤트 순서는 Semgrep 시작/종료, agent batch 시작/종료, verification 시작/종료, report 시작/종료다.

진행 단위는 Semgrep과 report가 0/1, agent와 verification은 원본 항목 완료 수/N이다. 재시도·배치 분할은 `total=N`을 바꾸지 않으며 한 항목이 terminal 상태가 될 때만 `current`를 올려 진행률이 감소하지 않는다.

| 환경변수 | 기본값 | 허용 범위 |

| `SAST_BATCH_MAX_CHARS` | 24000 | 1000~100000 |
| `SAST_BATCH_INPUT_TOKENS` | 12000 | 1000~64000 |
| `SAST_BATCH_OUTPUT_TOKENS` | 4000 | 512~16000 |
| `SAST_MAX_LLM_REQUESTS` | 250 | 1~1000 |
| `SAST_UPLOAD_MAX_MIB` | 25 | 1~100 |
| `SAST_UPLOAD_FILE_MAX_MIB` | 2 | 1~20 |
| `SAST_UPLOAD_MAX_FILES` | 500 | 1~5000 |
| `SAST_UPLOAD_EXTRACTED_MAX_MIB` | 100 | 1~500 |
| `SAST_MAX_SEMGREP_FINDINGS` | 5000 | 100~50000 |
| `NVIDIA_CONTEXT_WINDOW_TOKENS` | 32768 | 8192~1048576 |

값은 정수만 허용한다. 누락 시 기본값을 쓰고 형식·범위가 잘못되면 조용히 fallback하지 않고 시작 전에 설정명을 포함한 오류를 표시한다.

`core.config.RuntimeSettings.from_env()`가 API 제공자, 모델, 기존 `AnalysisLimits`, 배치, 업로드 한도를 한 번에 검증한다. `main.py`에서 설정을 만들고 `run_pipeline`에 전달하며 하위 모듈은 환경변수를 다시 읽지 않는다. 테스트는 환경변수 parsing과 모듈 동작을 분리한다.

### 실패와 후속 처리 계약

| 상황 | 단계 상태 | 후속 처리 | 사용자 표시 |
|---|---|---|---|
| Semgrep 미설치·비정상 종료 | failed | 뒤 단계 skipped | 설치 또는 stderr 요약 |
| findings가 있는데 API 키 없음·인증 실패 | agent failed | 검증 skipped, Semgrep-only 보고서 | 키 설정 안내 |
| findings 0건 | Semgrep completed | agent/검증 skipped, 빈 보고서 | 발견 없음 |
| 일부 배치 실패·예산 소진 | agent partial | 성공 결과만 검증·부분 보고서 | 실패/skipped 수 |
| JSON/ID 재시도 실패 | agent partial/failed | 유효 결과만 진행 | batch ID와 오류 코드 |
| 검증 일부 실패 | verification partial | tp만 승인 | verdict별 수량·근거 |
| 보고서 생성 실패 | report failed | UI snapshot 유지 | 재시도 가능한 오류 요약 |

### UI 와이어프레임

```text
+ Agentic SAST ---------------------------------------+
| 입력: (o 로컬 경로 / 파일 업로드)     [분석 시작]  |
| NVIDIA 키: 환경변수 감지 / 직접 입력(마스킹)       |
+ 1. Semgrep -------------------- [진행/완료/실패] --+
| 규칙, 심각도, 파일, 라인, 발견 건수                 |
+ 2. 에이전트 분석 -------------- [배치 2/5] --------+
| 배치별 대상, 주요 지점, 분석 요약, 경고             |
+ 3. 정탐/미탐 검증 ------------- [진행/부분완료] ----+
| TP/FP/기타 필터, 근거, 위험, 개선 방법              |
+ 4. 최종 보고서 ---------------- [완료] ------------+
| 요약, 미리보기, PDF/HTML, XLSX, JSON 다운로드       |
+-----------------------------------------------------+
```

각 섹션은 처음부터 빈 상태로 보이며 `st.status`, `st.progress`, `st.dataframe`, `st.expander`로 같은 컨테이너를 갱신한다. 실패 시 오류와 이미 확보한 결과, 후속 단계 상태를 함께 표시한다.

진행 이벤트는 새 항목 delta와 집계만 전달하며 매번 전체 snapshot을 복제하지 않는다. Semgrep snapshot은 서버에서 기본 5,000건까지 보존하고 초과 수를 warning으로 표시한다. UI는 200건씩 페이지로 렌더링하며 보존된 전체 snapshot을 별도 JSON으로 다운로드할 수 있다.

Semgrep snapshot과 LLM 분석 후보는 분리한다. 후보는 기존 `max_contexts=50`까지 severity 우선, rule·파일 round-robin 다양성, canonical finding ID tie-break 순서로 결정론적으로 선택한다. 제외된 결과는 `not_selected`로 UI에 남긴다. 실행 전 실제 batch 수 `B`를 계산해 분석+검증 `2B`, 최대 retry/split `4B`, 단건 보강 최대 `10*8` 호출을 예약하며 예산에 맞지 않으면 보강 수부터 줄인다.

## Success Criteria

- `python main.py` 한 번으로 localhost UI가 열리고 재귀 실행하지 않는다.
- 두 BAT와 기존 CLI 계약이 제거되고 활성 문서·테스트에 참조가 없다.
- 경로, ZIP 1개, 복수 소스 파일이 같은 파이프라인을 사용한다.
- 악성·제한 초과 업로드가 분석 전에 거부되고 임시 파일이 남지 않는다.
- 1차 분석 요청 수가 deterministic packer가 만든 배치 수와 같고, 최소 두 항목이 한 배치에 들어가는 fixture에서는 요청 수가 항목 수보다 작다. 모든 최초 요청은 항목·문자·추정 토큰 경계를 넘지 않는다.
- 모든 결과가 `context_id`로 파일·라인과 일치하며 누락·중복 응답을 탐지한다.
- UI가 네 단계를 실제 순서로 갱신하고 종료 후 snapshot을 유지한다.
- 정탐과 미탐, unknown/error/skipped가 근거와 개선안 또는 오류를 보존한다.
- 기존 PDF/HTML, XLSX, JSON과 민감 파일 정책이 회귀하지 않는다.
- 키가 로그, 예외, 보고서, 작업 로그에 노출되지 않는다.
- 동일·새 Streamlit 세션, 새 탭의 중복 제출에서도 프로세스당 활성 run은 하나뿐이다.
- ZIP symlink, 중복 정규화 경로, 대소문자·Unicode 충돌, Windows 예약명 테스트가 통과한다.

## Test Strategy

- `tests/unit/test_entrypoint.py`: 부모 실행의 `sys.executable -m streamlit run main.py`, 자식 플래그, 종료 코드, 인터럽트, 재귀 방지를 subprocess mock으로 검증한다.
- `tests/integration/test_ui_flow.py`: AppTest와 fake pipeline으로 입력 모드, 네 단계 순서, 부분 실패, 빈 결과, 다운로드 버튼 렌더링을 검증한다. 브라우저 전송 자체를 AppTest 성공으로 주장하지 않는다.
- 업로드 bytes, workspace, 상태 전이는 순수 서비스 단위 테스트로 검증하고, coordinator의 동시 실행·해제는 thread concurrency test로 검증한다.
- 실제 Streamlit subprocess를 임시 포트에서 실행해 health endpoint 응답, localhost bind, `.streamlit/config.toml`의 XSRF/CORS 적용, 정상 종료를 smoke test한다.
- 동일 세션 중복 클릭, 완료 후 rerun snapshot 보존, 새 run 상태 교체는 AppTest에서 검증한다.
- `tests/unit/test_batch_analysis.py`: pack 경계, canonical ID, 순서 보존, schema 누락/중복/미등록 ID, retry/split, 예산 소진을 fake LLM으로 검증한다.
- `tests/integration/test_nvidia_live.py`는 `live_nvidia` marker로만 실행한다. 두 항목을 분석 1회+검증 1회, 최대 2개 실제 요청으로 제한하고 ID 왕복, schema, TP/FP 매핑, 키 비노출을 검증한다.
- 기본 `pytest`에서는 live marker를 제외하며 실제 키가 없으면 live test를 skip한다. 응답 원문과 소스 전문은 snapshot으로 저장하지 않는다.
- `tests/unit/test_upload_workspace.py`: ZIP traversal, 절대/드라이브 경로, symlink·특수 파일, 중첩 ZIP, duplicate/case/Unicode canonical 충돌, Windows 예약명, 파일 수·개별·총 크기·압축률, loose-file basename 충돌을 검증한다.
- 업로드 성공, 검증 중 실패, 추출 중 한도 초과, pipeline 예외 모두에서 임시 작업공간 cleanup과 artifact bytes 보존 여부를 검증한다.
- `tests/unit/test_pipeline.py`: 실패 계약 표의 Semgrep 실패, 0건, 키/인증 실패, agent partial, verification partial, report failure를 parameterize하고 stage terminal 상태, 후속 skipped 여부, snapshot, 사용자 오류를 검증한다.
- **CRITICAL regression:** 잘못된 입력·scanner/agent/report 예외에서도 thread/process coordinator가 해제되고 다음 scan이 실행되며, 동시 두 번째 scan은 계속 거부되는지 검증한다.
- **CRITICAL regression:** 기존 PDF/HTML, XLSX, JSON 산출물과 명시 API 키의 환경변수 비변경, 민감·생성 경로 제외를 유지한다.

## Parallelization Strategy

| Step | Modules touched | Depends on |
|---|---|---|
| Foundation: settings·DTO·event contract | `core/`, `tests/unit/` | 없음 |
| Backend: batch·agent·pipeline·upload | `core/`, `tests/unit/`, `tests/integration/` | Foundation |
| UI: entrypoint·rendering·AppTest | `main.py`, `ui/`, `tests/integration/` | Foundation |
| Integration: docs·BAT removal·full verification | repo root, `docs/`, `tests/` | Backend + UI |

- Foundation은 먼저 순차 완료한다.
- 이후 Lane A Backend와 Lane B UI를 병렬 실행한다. UI는 contract fixture로 작업하고 backend 구현을 직접 import하지 않는다.
- 두 lane을 합친 뒤 Integration을 순차 실행한다.
- Backend와 UI가 `tests/integration/`을 함께 건드릴 수 있으므로 파일을 backend/live와 ui/flow로 분리해 충돌을 피한다.
