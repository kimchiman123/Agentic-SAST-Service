### 1. [HIGH] 사용자 입력이 eval()로 전달되어 코드 실행이 가능한 취약점
- **심각도:** HIGH
- **판정:** True Positive
- **규칙 ID:** `javascript.browser.security.eval-detected.eval-detected`
- **파일:** `payment_api.js`
- **출처:** 코드 정적 분석

**설명:** payment_api.js의 /api/eval 엔드포인트는 요청 본문(req.body.mathFormula)에서 받은 값을 검증 없이 eval()에 전달합니다. 외부 입력이 실행 엔진에 직접 연결되므로, 공격자가 임의의 JavaScript 코드를 주입해 서버 측 코드 실행 또는 비정상 동작을 유발할 수 있습니다.

**데이터 흐름 추적 (Taint Analysis):**
> Source: req.body.mathFormula -> Sink: eval(mathFormula). 입력값에 대한 허용 목록 검증, 파서 기반 제한, 또는 안전한 수식 평가 로직이 존재하지 않으며, 입력이 그대로 실행됩니다.

**공격 시나리오:**
> 공격자가 /api/eval에 {"mathFormula":"1+2"} 대신 코드 조각을 포함한 문자열을 전송하면, 서버는 해당 문자열을 eval()로 실행합니다. 결과적으로 계산 기능을 가장한 임의 코드 실행, 예기치 않은 객체 접근, 서비스 장애를 유발할 수 있습니다.

**취약 원본 코드:**
```
const { mathFormula } = req.body;
const result = eval(mathFormula);
```

**수정 패치 코드 (Remediation):**
```
const math = require('mathjs');

app.post('/api/eval', (req, res) => {
  const { mathFormula } = req.body;
  try {
    if (typeof mathFormula !== 'string' || !/^[0-9+\-*/().\s]+$/.test(mathFormula)) {
      return res.status(400).json({ error: 'Invalid formula' });
    }
    const result = math.evaluate(mathFormula);
    res.json({ result });
  } catch (e) {
    res.status(500).json({ error: 'Calculation failed' });
  }
});
```

**수정 가이드:** eval()를 제거하고, 허용된 산술식만 처리하는 안전한 파서/평가 라이브러리(mathjs 등)로 대체해야 합니다. 추가로 입력 형식을 화이트리스트 정규식으로 제한하여 함수 호출, 식별자, 할당, 체인 표현식을 차단해야 합니다.

**ISMS-P 위반 사항:**
> ISMS-P 암호/보안 취약점 관리 및 소프트웨어 보안성 확보 관점에서, 외부 입력 검증 없이 실행 기능을 제공하는 것은 안전하지 않은 개발 관행에 해당하며, 취약점 조치 및 코드 보안성 확보 요구사항에 저촉될 수 있습니다.

### 4. [HIGH] 사용자 입력이 eval()로 전달되어 임의 코드 실행이 가능한 취약점
- **심각도:** HIGH
- **판정:** True Positive
- **규칙 ID:** `javascript.lang.security.audit.code-string-concat.code-string-concat`
- **파일:** `payment_api.js`
- **출처:** 코드 정적 분석

**설명:** Express 요청 본문(req.body.mathFormula)에서 입력된 값이 검증 없이 eval(mathFormula)에 직접 전달됩니다. 이는 공격자가 임의의 JavaScript 식/코드를 주입하여 애플리케이션 프로세스 권한으로 실행하게 만들 수 있는 전형적인 코드 실행 취약점입니다. try/catch는 예외만 처리할 뿐 실행 자체를 차단하지 못하므로 방어 수단이 될 수 없습니다.

**데이터 흐름 추적 (Taint Analysis):**
> Source: req.body.mathFormula (클라이언트가 제어 가능한 요청 바디) -> Sink: eval(mathFormula) -> Result: 입력값이 그대로 JavaScript 실행 컨텍스트에 전달되어 코드 실행 가능. 전처리/화이트리스트/파서 기반 제한이 없어 taint가 차단되지 않음.

**공격 시나리오:**
> 공격자는 /api/eval 엔드포인트에 mathFormula로 '1+2' 같은 정상 수식뿐 아니라 ';process.mainModule...' 형태의 악성 표현식, 전역 객체 접근 시도, 환경정보 출력, 파일/명령 실행을 유도하는 JS 코드를 주입할 수 있습니다. 예를 들어 내부적으로 허용되는 실행 컨텍스트에 따라 프로세스 정보 노출, 서버 측 코드 실행, 추가 침해로 이어질 수 있습니다.

**취약 원본 코드:**
```
const { mathFormula } = req.body;
...
const result = eval(mathFormula);
```

**수정 패치 코드 (Remediation):**
```
const { Parser } = require('expr-eval');

app.post('/api/eval', (req, res) => {
  const { mathFormula } = req.body;

  if (typeof mathFormula !== 'string' || !/^[0-9+\-*/().\s]+$/.test(mathFormula)) {
    return res.status(400).json({ error: 'Invalid formula' });
  }

  try {
    const expr = Parser.parse(mathFormula);
    const result = expr.evaluate();
    return res.json({ result });
  } catch (e) {
    return res.status(400).json({ error: 'Calculation failed' });
  }
});
```

**수정 가이드:** eval()을 완전히 제거하고, 수학식만 처리 가능한 전용 파서/평가기(expr-eval, mathjs 등)로 대체해야 합니다. 최소한의 입력 검증으로 숫자와 산술 연산자만 허용하고, 세미콜론, 대입, 식별자, 프로퍼티 접근, 문자열, 함수 호출을 차단해야 합니다. 가능하면 수식 처리 로직은 별도 모듈로 격리하고, 허용 연산을 화이트리스트로 관리하세요.

**ISMS-P 위반 사항:**
> ISMS-P 2.6.7(암호연산) 직접 위반은 아니나, 안전하지 않은 코드 실행 로직으로 인해 애플리케이션 보호조치 미흡 및 중요정보/시스템 무결성 침해 가능성이 큼. 또한 1.1.4 범위 설정 관점에서 핵심 서비스에 영향을 주는 기능의 위험 통제가 필요하며, 관리체계 내 안전한 구현/검증 절차 미준수에 해당할 수 있음.

**취약 원본 코드:**

```
app.post('/api/eval', (req, res) => {
```

**수정 가이드:** eval 사용을 제거하고, 허용된 산술 연산만 처리하는 파서/검증 로직으로 대체해야 합니다. 최소한의 화이트리스트 정규식 검증을 적용하고, 가능하면 전용 수식 파서 라이브러리를 사용해야 합니다. 임의 객체 접근, 함수 호출, 식별자 사용을 차단해야 합니다.

**ISMS-P 위반 사항:**
> ISMS-P 관점에서 입력값 검증 미흡으로 인한 안전하지 않은 코드 실행 통제 위반 가능성이 있습니다.

### 6. [HIGH] 이체 API의 계정 소유권 검증 부재로 인한 IDOR/권한상승
- **심각도:** HIGH
- **판정:** True Positive
- **규칙 ID:** `javascript.lang.security.audit.idor-detected`
- **파일:** `payment_api.js`
- **출처:** 코드 정적 분석

**설명:** /api/transfer에서 로그인 사용자(loggedInUser)와 fromAccount의 일치 여부를 검증하지 않아, 요청자가 타인의 계좌를 출금 계좌로 지정할 수 있습니다. 또한 amount 음수 검증이 없어 잔액 조작이 가능합니다.

**데이터 흐름 추적 (Taint Analysis):**
> Source는 req.headers['x-user-id'] 및 req.body.fromAccount, toAccount, amount입니다. Sink는 usersDB[fromAccount].balance -= amount; usersDB[toAccount].balance += amount; 입니다. fromAccount의 소유권 검증이 없고 amount의 부호 검증도 없어, 인증된 사용자의 요청이 타인 계좌의 잔액을 임의로 변경할 수 있습니다.

**공격 시나리오:**
> 공격자는 x-user-id를 자신의 값으로 두고 body에 victim 계좌를 fromAccount로, 자신의 계좌를 toAccount로 넣어 타인 계좌에서 자금을 이체할 수 있습니다. 또한 amount=-10000을 전송하면 fromAccount는 증가하고 toAccount는 감소해 잔액 역전이 발생합니다.

**취약 원본 코드:**
```
const loggedInUser = req.headers['x-user-id'];
...
if (usersDB[fromAccount].balance < amount) {
  return res.status(400).json({ error: "Insufficient balance" });
}

usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
```

**수정 패치 코드 (Remediation):**
```
app.post('/api/transfer', (req, res) => {
  const loggedInUser = req.headers['x-user-id'];
  const { fromAccount, toAccount, amount } = req.body;

  if (!loggedInUser || loggedInUser !== fromAccount) {
    return res.status(403).json({ error: 'Forbidden' });
  }

  if (!Number.isInteger(amount) || amount <= 0) {
    return res.status(400).json({ error: 'Invalid amount' });
  }

  if (!usersDB[fromAccount] || !usersDB[toAccount]) {
    return res.status(404).json({ error: 'Account not found' });
  }

  if (usersDB[fromAccount].balance < amount) {
    return res.status(400).json({ error: 'Insufficient balance' });
  }

  usersDB[fromAccount].balance -= amount;
  usersDB[toAccount].balance += amount;
  return res.json({ success: true });
});
```

**수정 가이드:** 인증된 사용자와 출금 계좌의 소유권을 반드시 일치시켜야 하며, amount는 양의 정수로만 허용해야 합니다. 또한 인증은 임시 헤더가 아니라 실제 세션/토큰 기반으로 수행해야 합니다. 이체 로직은 서버측 권한 검증 후에만 실행되도록 하고, 감사 로그를 남겨야 합니다.

**ISMS-P 위반 사항:**
> ISMS-P 2.5.2 정보시스템 접근 및 최소권한 원칙 위반 가능성이 있으며, 비인가자 접근 통제 미흡에 해당할 수 있습니다.

### 8. [WARNING] 비밀번호 검증에 MD5를 사용
- **심각도:** WARNING
- **판정:** True Positive
- **규칙 ID:** `javascript.lang.security.audit.md5-used-as-password.md5-used-as-password`
- **파일:** `payment_api.js`
- **출처:** 코드 정적 분석

**설명:** 로그인 처리에서 사용자 입력 password를 MD5로 해시한 뒤 저장된 passwordHash와 비교하고 있습니다. MD5는 비밀번호 해시용으로 안전하지 않으며, 솔트와 느린 해시 알고리즘이 없어 사전 공격 및 빠른 크래킹에 취약합니다. 따라서 Semgrep 탐지는 실제 취약점(True Positive)입니다.

**데이터 흐름 추적 (Taint Analysis):**
> Source는 req.body.password이며, Sink는 crypto.createHash('md5').update(password).digest('hex')입니다. 이후 생성된 해시는 usersDB[username].passwordHash와 비교되어 인증에 사용됩니다. 공격자는 요청 본문을 통해 password를 자유롭게 제어할 수 있으므로, 입력값이 직접 약한 MD5 비밀번호 검증 로직으로 전달되는 경로가 성립합니다.

**공격 시나리오:**
> 공격자는 유출된 계정 해시 또는 추정 가능한 비밀번호 목록을 이용해 MD5 사전/레인보우 테이블 공격을 수행할 수 있습니다. 예를 들어 admin의 하드코딩된 MD5 해시(21232f297a57a5a743894a0e4a801fc3)는 매우 짧은 시간 내 원문(admin)으로 복원될 수 있으며, 이후 해당 비밀번호로 로그인해 토큰을 획득할 수 있습니다.

**취약 원본 코드:**
```
const hash = crypto.createHash('md5').update(password).digest('hex');
```

**수정 패치 코드 (Remediation):**
```
const bcrypt = require('bcrypt');

app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  const user = usersDB[username];
  if (!user) {
    return res.status(401).json({ success: false, msg: 'Invalid credentials' });
  }

  const ok = await bcrypt.compare(password, user.passwordHash);
  if (ok) {
    return res.json({ success: true, token: `fake-jwt-token-for-${username}` });
  }
  return res.status(401).json({ success: false, msg: 'Invalid credentials' });
});
```

**수정 가이드:** MD5 기반 비교를 제거하고 bcrypt, scrypt, argon2 같은 느린 비밀번호 해시 알고리즘으로 변경해야 합니다. 저장값은 bcrypt 해시 문자열로 재생성해야 하며, 기존 MD5 해시는 마이그레이션 또는 강제 비밀번호 재설정을 통해 폐기해야 합니다. 추가로 로그인 실패 시 동일한 응답을 유지하고, 필요 시 레이트 리밋과 계정 잠금 정책을 적용하는 것이 좋습니다.

**ISMS-P 위반 사항:**
> ISMS-P 2.6.7 암호연산: 취약한 해시 알고리즘(MD5) 사용 금지 및 안전한 암호연산 적용 요구에 위반될 수 있습니다.

### 1. [CRITICAL] 송금 API의 출금 계좌 소유권 검증 부재로 인한 IDOR/권한 우회
- **심각도:** CRITICAL
- **유형:** `IDOR`
- **파일:** `payment_api.js`
- **출처:** 비즈니스 로직 심층 분석

**설명:** `/api/transfer`는 요청 헤더의 `x-user-id`를 인증 정보처럼 받지만, 실제로 `fromAccount`가 해당 사용자 소유인지 검증하지 않습니다. 그 결과 공격자는 임의의 타인 계좌를 `fromAccount`로 지정해 잔액을 변경할 수 있어, 계정 소유권을 기반으로 한 접근통제가 깨집니다.

**데이터 흐름 추적 (Taint Analysis):**
> 클라이언트 입력(`req.headers['x-user-id']`, `req.body.fromAccount`)이 서버 측 권한검증 없이 바로 자산 변경 로직(`usersDB[fromAccount].balance`)에 도달합니다. 인증 주체와 대상 계좌의 매핑 검증이 없어서, 요청자가 타인 계좌를 조작해도 차단되지 않습니다.

**공격 시나리오:**
> 공격자가 자신의 세션 또는 헤더에 임의 값을 넣은 뒤, `fromAccount`에 관리자나 타인 계좌를 넣고 `toAccount`를 자신의 계좌로 지정해 송금을 수행하면 타인의 자산이 감소합니다.

**취약 원본 코드:**
```
const loggedInUser = req.headers['x-user-id']; 
const { fromAccount, toAccount, amount } = req.body;

if (!usersDB[fromAccount] || !usersDB[toAccount]) {
    return res.status(404).json({ error: "Account not found" });
}

usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
```

**수정 패치 코드 (Remediation):**
```
app.post('/api/transfer', (req, res) => {
    const loggedInUser = req.user.id; // 서버 검증된 인증정보 사용
    const { fromAccount, toAccount, amount } = req.body;

    if (fromAccount !== loggedInUser) {
        return res.status(403).json({ error: 'Cannot transfer from another user\'s account' });
    }
    if (!Number.isInteger(amount) || amount <= 0) {
        return res.status(400).json({ error: 'Invalid amount' });
    }
    if (!usersDB[fromAccount] || !usersDB[toAccount]) {
        return res.status(404).json({ error: 'Account not found' });
    }
    if (usersDB[fromAccount].balance < amount) {
        return res.status(400).json({ error: 'Insufficient balance' });
    }

    usersDB[fromAccount].balance -= amount;
    usersDB[toAccount].balance += amount;
    res.json({ success: true, msg: 'Transfer complete' });
});
```

**수정 가이드:** 클라이언트가 전달한 헤더 값을 인증 근거로 사용하지 말고, 서버에서 검증된 세션/토큰 기반 사용자 ID를 사용해야 합니다. 또한 출금 계좌가 인증된 사용자 본인 소유인지 반드시 확인한 뒤 이체를 허용해야 합니다.

**ISMS-P 위반 사항:**
> 개인정보의 안전성 확보조치 기준 제4조, 제6조 / ISMS-P 2.11.2 취약점 점검 및 조치

### 2. [CRITICAL] 음수 금액 처리 누락으로 인한 송금 로직 반전(Logic Bypass)
- **심각도:** CRITICAL
- **유형:** `Logic Bypass`
- **파일:** `payment_api.js`
- **출처:** 비즈니스 로직 심층 분석

**설명:** `amount`에 대한 양수/정수 검증이 없어 음수 값을 그대로 처리할 수 있습니다. 이 경우 `balance < amount` 검사가 의미를 잃고, 차감/증가 연산이 반대로 동작하여 출금 계좌 잔액이 오히려 증가하고 수취 계좌 잔액이 감소할 수 있습니다.

**데이터 흐름 추적 (Taint Analysis):**
> 외부 입력인 `req.body.amount`가 검증 없이 잔액 비교 및 산술 연산에 사용됩니다. 특히 음수 값은 비교 조건과 `-=` / `+=` 연산의 의미를 뒤집어, 금액 이전이 아닌 자산 조작을 유발합니다.

**공격 시나리오:**
> 공격자가 `amount: -10000`으로 요청하면 `usersDB[fromAccount].balance -= amount`는 10000 증가가 되고, `toAccount`는 10000 감소합니다. 이를 통해 잔액 조작, 타인 계좌 훼손, 비정상 자금 이동이 가능합니다.

**취약 원본 코드:**
```
if (usersDB[fromAccount].balance < amount) {
    return res.status(400).json({ error: "Insufficient balance" });

// 이체 수행
usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
```

**수정 패치 코드 (Remediation):**
```
if (!Number.isInteger(amount) || amount <= 0) {
    return res.status(400).json({ error: 'Amount must be a positive integer' });
}
if (usersDB[fromAccount].balance < amount) {
    return res.status(400).json({ error: 'Insufficient balance' });
}
usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
```

**수정 가이드:** 금액은 반드시 양의 정수로만 허용하고, 0/음수/소수/비정상 범위를 선제 차단해야 합니다. 비교와 연산 전에 입력 정규화와 타입 검증을 추가하여 송금 의미가 뒤집히는 경우를 막아야 합니다.

**ISMS-P 위반 사항:**
> 개인정보의 안전성 확보조치 기준 제4조 / ISMS-P 2.11.2 취약점 점검 및 조치

### 3. [HIGH] 잔액 검사와 갱신이 원자적으로 보호되지 않아 동시성 경쟁 조건 발생
- **심각도:** HIGH
- **유형:** `Race Condition`
- **파일:** `payment_api.js`
- **출처:** 비즈니스 로직 심층 분석

**설명:** `/api/transfer`는 잔액 확인과 잔액 변경을 분리된 일반 객체 연산으로 수행합니다. 다중 요청이 동시에 들어오면 동일 잔액에 대해 중복 승인이나 비정상 잔액 상태가 발생할 수 있어 자금 무결성이 깨집니다.

**데이터 흐름 추적 (Taint Analysis):**
> 동일한 `usersDB[fromAccount]`에 대해 여러 요청이 병렬로 처리될 수 있는데, 검사(`balance < amount`)와 갱신(`-=`, `+=`) 사이에 락/트랜잭션이 없습니다. 따라서 두 요청이 같은 초기 잔액을 기준으로 동시에 통과할 수 있습니다.

**공격 시나리오:**
> 공격자가 같은 계좌에서 거의 동시에 여러 개의 이체 요청을 보내면, 각 요청이 동일한 잔액을 보고 승인될 수 있습니다. 그 결과 실제 잔액보다 많은 금액이 이체되거나 계좌 상태가 비정상적으로 변합니다.

**취약 원본 코드:**

```
if (usersDB[fromAccount].balance < amount) {
    return res.status(400).json({ error: "Insufficient balance" });
}

usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
```

```
// 예시: 계좌별 락 또는 DB 트랜잭션 사용
```
