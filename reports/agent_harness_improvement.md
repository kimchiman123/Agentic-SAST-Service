
- **영향을 받는 코드**:
  ```javascript
  20: const hash = crypto.createHash('md5').update(password).digest('hex');
22: if (usersDB[username] && usersDB[username].passwordHash === hash) {
  ```
- **개선된 추론 흐름 (Decision Tree)**:

  | 사용자 입력 password가 인증 검증에 사용됨을 확인 | 사용자 입력(password)이 로그인 API로 유입됨 확인 |

  | 비밀번호 저장/검증에 MD5 사용은 안전하지 않음을 판단 | 해시값이 인증 비교에 사용되어 계정 접근을 결정함 확인 |
  | 오프라인 크래킹 및 계정 탈취 가능성을 도출 | MD5가 비밀번호 저장/검증에 부적절하고 크래킹에 취약함 판단 |

  * **1차**: 보안 요구사항 정의 및 검토 관점에서 금액의 유효 범위(양수, 정수, 한도)를 설계·검증하지 않아 입력값 논리 우회가 발생합니다. 전자거래/핀테크 처리에서는 금전 흐름의 방향성과 경계를 명확히 해야 하며, 검증 누락은 개발 단계 보안 요구사항 정의 미흡에 해당합니다.
  * **2차**: 개인정보 및 중요 데이터의 품질과 무결성을 보장해야 합니다. 현재 로직은 입력값 검증이 부족하여 금액의 정상성(양수, 정수, 범위)을 보장하지 못하므로 자산 데이터의 정확성을 훼손합니다. 추가적으로 비정상 입력에 대한 예외처리와 감사기록을 적용해야 합니다.
- **영향을 받는 코드**:
  ```javascript
  if (usersDB[fromAccount].balance < amount) {
    return res.status(400).json({ error: "Insufficient balance" });
}

usersDB[fromAccount].balance -= amount;
usersDB[toAccount].balance += amount;
  ```
- **개선된 추론 흐름 (Decision Tree)**:
  | 1차 실행 의사결정 흐름 | 2차 실행 의사결정 흐름 |
  | :--- | :--- |
  | amount 입력값이 검증 없이 사용되는지 확인 | 금액 입력값의 검증 조건을 확인 |
  | balance < amount 비교가 음수 입력에서 무력화되는지 점검 | 잔액 비교가 음수 값에서 의미를 잃는다는 점을 도출 |
  | amount=-10000에서 차감/가산 연산이 역전됨을 도출 | 차감/증가 수식에 음수 값이 그대로 반영됨을 확인 |
  | 금액 역전으로 자산 조작이 실제로 가능함을 확인 | 잔액 역전과 타인 계좌 손실이 발생하는지 시나리오로 검증 |
  | ISMS-P 2.8.1 관점의 입력 검증 요구사항 미정의/미이행으로 확정 | 논리 우회 취약점으로 확정하고 ISMS-P 3.2.2에 매핑 |

#### [6] 사용자 입력이 eval()로 전달되는 코드 인젝션 취약점 (`payment_api.js`)
- **취약점 유형**: `Code Injection` (1차 vs 2차 일치)
- **심각도 등급**: 1차 `[HIGH]` vs 2차 `[CRITICAL]` (불일치)
- **매핑된 ISMS-P 코드**: 1차 `[2.6.2]` vs 2차 `[2.6.2]` (일치)
- **ISMS-P 설명**:
  * **1차**: 외부 입력값이 검증 없이 코드 실행 경로로 전달되어 비인가된 스크립트/명령 실행 가능성이 존재합니다. 안내서의 코드 인젝션 항목(2.6.2 취지)에 비추어 볼 때, 입력값 검증 및 화이트리스트 적용이 미흡하며 허용되지 않은 코드 실행을 방지하지 못하고 있습니다. 제로트러스트 원칙상 입력은 신뢰하지 않고 최소 권한으로 처리해야 하므로, `eval` 제거 및 안전한 파서 적용이 필요합니다.
  * **2차**: 외부 입력을 검증 없이 명령/코드 실행으로 연결하는 구조는 웹 애플리케이션의 코드 인젝션 방지 요구에 위배됩니다. ISMS-P 기술적 취약점 분석·평가 항목의 ‘코드 인젝션’에서 요구하는 것처럼, 임의 입력값이 명령으로 실행되지 않도록 화이트리스트 검증과 안전한 처리 방식이 필요합니다. 현재 구현은 ‘임의의 입력값에 대하여 검증 없이 명령이 실행되는 경우’에 해당하므로 취약으로 판단됩니다.
- **영향을 받는 코드**:
  ```javascript
  32~37: `const { mathFormula } = req.body;` / `const result = eval(mathFormula);`
  ```
- **개선된 추론 흐름 (Decision Tree)**:
  | 1차 실행 의사결정 흐름 | 2차 실행 의사결정 흐름 |
  | :--- | :--- |
  | 요청 바디의 사용자 제어 입력 `mathFormula` 확인 | `express.json()` 기반으로 외부 요청 본문이 `req.body`로 유입됨을 확인 |
  | 검증/필터링 없이 `eval(mathFormula)`로 직접 전달되는 경로 확인 | `mathFormula`가 사용자 제어 입력이며 별도 검증/화이트리스트가 없음을 확인 |
  | 사용자 입력이 실행 컨텍스트에 도달하므로 코드 인젝션 가능성 도출 | `eval(mathFormula)`로 직접 실행되는 타인트 경로를 확인 |
  | ISMS-P 웹 취약점 가이드의 '코드 인젝션' 기준에 부합 | 임의 JavaScript 실행 및 원격 코드 실행(RCE) 가능성 도출 |
  | 따라서 Semgrep 경고는 실제 취약점(True Positive)로 판정 | ISMS-P 코드 인젝션 통제 요구(화이트리스트/입력 검증) 위반으로 매핑 |

#### [7] 비밀번호를 안전한 일방향 암호화 없이 저장하는 로직 결함 (`advanced_logic_api.js`)
- **취약점 유형**: `Other` (1차 vs 2차 일치)
- **심각도 등급**: 1차 `[HIGH]` vs 2차 `[INFO]` (불일치)
- **매핑된 ISMS-P 코드**: 1차 `[D-08]` vs 2차 `[2.6.3]` (불일치)
- **ISMS-P 설명**:
  * **1차**: 안전한 암호화 알고리즘 사용 요건에 부합하지 않습니다. 참조 기준은 SHA-256 이상 또는 SHA-2 계열의 안전한 비밀번호 암호화 알고리즘 사용을 요구하며, 비밀번호 저장 시 평문 저장은 기밀성과 무결성을 모두 훼손합니다. 또한 ISMS-P 암호화 적용 지침의 '비밀번호에 대한 안전하지 않은 MD5 사용 사례'보다 더 직접적인 위반으로 볼 수 있습니다.
  * **2차**: ISMS-P 2.6.3 응용프로그램 접근 관점에서, 세션/인증이 필요한 응용프로그램은 접근통제와 세션 보호가 명확해야 합니다. 쿠키 기반 세션을 사용하면서 CSRF 방어가 없다면 사용자의 인증 상태를 악용한 비인가 요청 가능성이 있어 응용프로그램 접근 통제의 무결성이 약화됩니다. 또한 OT 제로트러스트 원칙 중 '모든 접근에 대해 신뢰하지 않을 것' 및 '세션 단위 접근 허용, 통신 보호'에 부합하도록 명시적 검증과 세션 보호를 강화해야 합니다.
- **영향을 받는 코드**:
  ```javascript
  usersDB[targetUser].password = newPassword;
  ```
- **개선된 추론 흐름 (Decision Tree)**:
  | 1차 실행 의사결정 흐름 | 2차 실행 의사결정 흐름 |
  | :--- | :--- |
  | 비밀번호 저장 코드에서 해시/솔트 적용 여부 확인 | CSRF 미들웨어 미탐지 규칙과 `express()` 생성 지점 확인 |
  | 재설정 경로가 평문 대입임을 식별 | 전체 문맥에서 세션/쿠키 기반 인증 여부와 상태 변경 영향도 미확인 |
  | 로그인 경로의 해시 저장 방식과 재설정 경로의 불일치 확인 | 따라서 공격자 제어 입력이 취약점으로 이어진다고 단정 불가 |
  | 저장소 유출 시 즉시 계정 노출 가능성 평가 | 현재는 INFO 수준 조건부 경고로 분류 |
  | 안전한 비밀번호 암호화 미적용으로 컴플라이언스 위반 매핑 | 쿠키/세션 사용 시 CSRF 토큰, SameSite, Origin 검증 적용 필요 |
